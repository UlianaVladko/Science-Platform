# Научный атлас — техническое и пользовательское руководство проекта

> **Назначение документа.** Это обзор текущего состояния большого проекта: архитектуры, реализованных пользовательских сценариев, контрактов, источников данных, режимов запуска и ответственности каталогов. Документ описывает содержимое этой поставки, а не историю последних исправлений.

## 1. Кратко о проекте

«Научный атлас» — веб-платформа для исследования научной литературы как связанного информационного пространства. Она объединяет каталог научных дисциплин, поиск публикаций, страницы публикаций и авторов, библиографические связи, аналитические панели и пользовательский раздел вопросов и ответов.

Система собрана из трёх основных частей:

1. **Web UI** — клиентское приложение React + TypeScript.
2. **BFF (Backend for Frontend)** — промежуточный HTTP-сервис на Go. Он предоставляет фронтенду единый API, объединяет источники, формирует демонстрационные данные и обслуживает пользовательское состояние, которого нет во внешнем API.
3. **Literature API** — согласованный REST API на FastAPI, поставляемый в `vendor/literature-api`.

Проект рассчитан на демонстрацию полного пользовательского пути и интеграционных контрактов. Это не следует путать с полностью промышленной платформой: входящие API- и BFF-адаптеры в этой версии используют mock/fixture-данные, поиск BFF работает через mock-движок, а NLP и долговременное хранилище не подключены.

## 2. Архитектура и движение запроса

```text
Пользователь / браузер
        |
        v
React + TypeScript (web)
        |  HTTP /api/*
        v
Nginx (контейнер web; проксирование /api)
        |
        v
Go BFF :8080
   |          |             |
   |          |             +--> BFF Store (Q&A, likes, follows; RAM)
   |          +----------------> Demo Corpus + Synthetic Widgets
   |
   +--> Literature API :8000 (если доступен / включён профиль full)

Literature API:
FastAPI routers -> application services -> ports -> mock adapters -> fixtures
```

Фронтенд не обращается напрямую к FastAPI. Он использует единый префикс `/api`, который Nginx передаёт BFF. BFF решает, откуда получить данные: из внешнего API, демонстрационного корпуса или собственного оперативного хранилища.

### 2.1 Зачем нужен BFF

BFF — не просто reverse proxy. Его задачи:

- дать фронтенду единый, стабильный контракт;
- согласовать формат данных разных источников;
- объединять результаты API и демо-поиска, убирать дубликаты и объединять фасеты;
- обеспечивать работу интерфейса, когда API недоступен;
- обслуживать дополнительные пользовательские функции (вопросы, ответы, голоса, лайки, подписки);
- формировать демонстрационные аналитические виджеты и графы;
- явно маркировать источник данных через `source` и сообщать состояние интеграции через `/api/health` и `/api/meta`.

### 2.2 Основные сущности

- **Publication** — публикация с метаданными, аннотацией, авторами, категориями, ключевыми словами, понятиями и метриками.
- **Author** — исследователь и его публикационная активность.
- **Category / Discipline** — дерево научной классификации.
- **Reference** — направленная библиографическая связь между публикациями.
- **Question / Answer** — обсуждение научных вопросов.
- **Graph** — узлы и рёбра цитирования, соавторства или понятий.
- **Dashboard Widget** — самостоятельный аналитический блок с данными и состоянием готовности.

## 3. Источники данных и режимы работы

Ключевое правило проекта: **демонстрационные данные не должны выдаваться за данные реального API**. Ответы и сущности помечаются полем `source`, а доступность upstream видна в интерфейсе.

| Маркер | Источник | Что предоставляет | Ограничения |
|---|---|---|---|
| `api` | Literature API (FastAPI) | Категории, поиск, карточки публикаций, авторов, аналитику, графы, операции с файлами и задачами по API-контракту | В поставке API использует mock-адаптеры и fixture-корпус; это не подключённая промышленная БД или настоящий поисковый/NLP-движок |
| `demo` | Синтетический корпус BFF | Расширенный детерминированный корпус: 218 публикаций, 64 автора, классификатор из 15 дисциплин и 38 подкатегорий, данные для поиска, карточек, аналитики и графов | Данные искусственные, создаются генератором; не являются реальной библиографической статистикой |
| `bff` | Состояние самого BFF | Q&A, ответы и голоса, лайки, просмотры/состояние взаимодействия, подписки и вспомогательные факты | Хранится в оперативной памяти процесса; после перезапуска сбрасывается |
| `demo-mock` | Демонстрационная подстановка метаданных | Ответы lookup по DOI/названию в форме добавления публикации | Не обращается к Crossref или иному внешнему реестру |

### 3.1 Demo mode — основной автономный режим

Запуск `docker compose up --build` поднимает BFF и Web UI без обязательного контейнера API. BFF генерирует свой корпус и обслуживает витрину. Если upstream не отвечает, интерфейс остаётся работоспособным на демо-данных, а `/api/health` сообщает `upstream: "down"`.

Демо-корпус генерируется детерминированно с фиксированным seed/снимком. Поэтому повторные запуски дают стабильные публикации, авторов, распределения и графики. Это удобно для тестирования интерфейса и воспроизводимых демонстраций.

### 3.2 Full mode — интеграционный режим

Запуск `docker compose --profile full up --build` дополнительно включает контейнер FastAPI на порту 8000. BFF обращается к нему по адресу `http://api:8000` внутри Docker-сети.

В full mode BFF использует API там, где доступны соответствующие операции, и дополняет/поддерживает функциональность демо-корпусом и собственным состоянием. Конкретный маршрут может иметь разный приоритет источников; ориентироваться нужно на `source` в ответе, а не предполагать, что весь экран целиком пришёл из API.

**Важно о размере данных:** fixture API в этой поставке содержит 4 публикации, 3 автора и 3 категории. Это небольшой согласованный пример контракта. Демонстрационный корпус BFF существенно больше (218 публикаций и 64 автора). Поэтому агрегаты API и BFF могут различаться — это ожидаемо при сравнении разных наборов данных.

### 3.3 Доступность upstream и деградация

- `/api/health` проверяет доступность BFF и сообщает состояние upstream.
- `/api/meta` сообщает URL/описания источников, версию, размер демо-корпуса, число авторов, поисковый движок и готовность виджетов.
- При сбое upstream BFF старается обслужить поддерживаемые сценарии из демо-корпуса.
- Для поиска поле `degraded` позволяет фронтенду понять, что выдача собрана в деградированном режиме.
- Фронтенд отображает индикатор «API онлайн» либо «демо-режим».

### 3.4 Что означает «API» в текущей версии

В проект включён полноценный каркас API с 20 публичными операциями, типизированными схемами, OpenAPI, тестами и mock-адаптерами. Однако README API прямо фиксирует, что настоящие хранилища, поисковые алгоритмы, NLP-пайплайны и аналитические вычисления пока не реализованы. Следовательно, наличие работающего endpoint не означает, что за ним уже стоит промышленный алгоритм или реальная база данных.

## 4. Пользовательские разделы и реализованные сценарии

### 4.1 Главная страница

- знакомство с платформой и быстрый переход к поиску;
- сводные показатели корпуса;
- карточки научных дисциплин;
- подборка публикаций.

### 4.2 Каталог дисциплин

- иерархия из 15 верхнеуровневых дисциплин и 38 подкатегорий в демо-классификаторе;
- переход от дисциплины к её подкатегориям;
- количество публикаций и описательные данные;
- факты по дисциплинам формируются BFF и маркируются `source: "bff"`.

### 4.3 Поиск

- поиск публикаций и поддерживаемые типы сущностей;
- режимы `hybrid`, `exact`/lexical и смысловой режим в интерфейсном контракте;
- фильтры по дисциплине/категории, году, типу публикации, языку и автору;
- фасеты и подсказки;
- сортировка по релевантности, дате, цитированиям, просмотрам и загрузкам;
- объединение API и demo-результатов с дедупликацией по ID в режиме `scope=all`.

Текущий BFF использует `search.MockEngine`. Это точка расширения, а не законченная реализация полнотекстового или семантического поиска. В коде предусмотрен интерфейс `search.Engine`, который позволяет подключить отдельный поисковый сервис (в том числе предполагаемый C++-движок), не переписывая HTTP-обработчики.

### 4.4 Карточка публикации

- библиографические метаданные и аннотация;
- авторы, ключевые слова и понятия;
- исходящие и входящие библиографические связи;
- похожие публикации;
- просмотры и лайки;
- работа с файлами там, где источник поддерживает файловый контракт.

### 4.5 Профиль автора

- сведения об авторе;
- список публикаций;
- статистика по годам и категориям;
- соавторы и граф соавторства;
- подписка на автора.

### 4.6 Аналитика

BFF предоставляет набор отдельных dashboard-виджетов: временные ряды публикаций и цитирований, распределения по категориям/языкам/типам/статусам/источникам/аффилиациям, рейтинги авторов и публикаций, распределение соавторства, тепловая карта активности и граф цитирования.

Часть виджетов зависит от NLP: облако ключевых слов, топ понятий и частотность лемм. По умолчанию `SYNTHETIC_NLP_READY=false`, поэтому такие виджеты должны показывать состояние «Данные готовятся». Переменная управляет демонстрационным флагом готовности, но сама по себе не запускает NLP-пайплайн.

Визуальный принцип: основная оболочка интерфейса сдержанная и нейтральная; диаграммы, графы и схемы используют различимые цвета, чтобы категории, серии и связи можно было визуально сопоставлять.

### 4.7 Вопросы и ответы (Q&A)

- список вопросов;
- создание вопроса;
- просмотр карточки вопроса;
- публикация ответов;
- голосование за ответы.

Это функциональность BFF, а не часть 20-операционного контракта Literature API. Состояние хранится в памяти.

### 4.8 Добавление публикации

- форма создания карточки;
- подстановка демонстрационных метаданных по DOI или названию;
- отправка создания через BFF;
- если upstream недоступен, BFF может создать демо-запись и явно пометить её источником `demo`.

Автоподстановка сейчас детерминированная mock-функция (`demo-mock`), не запрос к внешнему DOI-реестру.

## 6. Frontend: технологии и принципы

- **React 19** — компонентная модель интерфейса.
- **TypeScript 5.9** — типизация компонентов, моделей и API-ответов.
- **Vite 7** — dev server и production build.
- **React Router 7** — маршрутизация страниц.
- **Apache ECharts 6** — диаграммы и аналитические графики.
- **d3-force** — раскладка и физическая симуляция сетевых графов.
- **Nginx** — production-раздача собранной SPA и проксирование `/api`.

Разделение frontend по слоям:

- `pages` — композиция пользовательских экранов;
- `components` — переиспользуемые визуальные элементы;
- `components/charts` — специализированные визуализации;
- `api` — сетевой слой и типы контрактов;
- `hooks` — общие React hooks;
- `styles` — токены и оформление.

`web/index.html` — статическая HTML-оболочка React, не Go template. В текущем проекте серверные HTML-шаблоны на Go не используются. Если в дальнейшем BFF начнёт рендерить HTML, следует применять `html/template`, а не `text/template`.

## 7. BFF на Go: технологии и принципы

- Go 1.22;
- стандартная библиотека `net/http` и `ServeMux` с method-aware routes;
- без внешних Go-модулей;
- разделение на `api`, `domain`, `corpus`, `search`, `upstream`, `synthetic`, `enrich`;
- composition root в `cmd/server/main.go`;
- graceful shutdown через `signal.NotifyContext` и `http.Server.Shutdown`;
- таймауты HTTP-сервера заданы явно;
- middleware обеспечивает единое служебное поведение, включая request ID.

### 7.1 Поисковый порт

`search.Engine` — интерфейс, отделяющий обработчики от конкретного алгоритма. Текущая реализация `MockEngine` предназначена для демонстрации и тестирования. Реальный движок должен реализовать поиск и подсказки, возвращая доменные результаты. Это позволяет интегрировать отдельный сервис без переписывания страниц и маршрутов BFF.

### 7.2 Состояние

`enrich.Store` содержит интерактивные данные BFF. В этой версии они in-memory: данные живут в рамках процесса и не переживают его перезапуск. Для многорепличного production-развёртывания понадобится внешнее хранилище и определённая модель идентификации пользователя.

## 8. Literature API: структура и контракт

Встроенный API — отдельное приложение на Python 3.12+, FastAPI и Pydantic v2. Его внутренняя схема следует упрощённой архитектуре ports-and-adapters:

`HTTP router → application service → port (Protocol) → infrastructure adapter`.

- `api/routers` — HTTP-уровень: параметры, вызов сервиса, HTTP-ответ;
- `application/ports.py` — абстракции зависимостей;
- `application/services.py` — фасады прикладных операций;
- `domain` — предметные модели и исключения;
- `schemas` — типизированные входные DTO и схемы ошибок;
- `infrastructure/adapters.py` — mock реализации портов;
- `infrastructure/store.py` — общее состояние одного экземпляра приложения;
- `fixtures` — тестовый связанный корпус и образцы файлов.

API документирует **20 публичных операций под `/api/v1`**. К ним относятся классификация, поиск и подсказки, публикации и файлы, авторы, аналитика и агрегаты, графы, задачи обработки и кластеризация. Полный список методов, параметров, DTO, валидации и ограничений находится в `vendor/literature-api/README.md` и экспортированном `openapi.json`.

API использует fixture-данные и mock adapters. Задачи анализа в этой версии моделируют контракт и статусы, но не запускают настоящий NLP/кластеризационный вычислительный процесс.

## 9. Контракт BFF ↔ Frontend

`CONTRACT.md` — основной документ для согласования frontend и BFF. В нём описаны:

- группы endpoint и HTTP-методы;
- query/body параметры;
- структуры ответов;
- поля `source`;
- правила объединения API и demo результатов;
- readiness аналитических виджетов;
- Q&A, подписки, лайки и пользовательские заголовки.

Базовый префикс фронтенда — `/api`. Ответы JSON кодируются в UTF-8. Ошибки BFF оформляются единым конвертом `error` с кодом, сообщением, деталями и `request_id`. Клиентам следует опираться на реальные ответы и типы, а не дублировать логику источников в компонентах.

## 10. Основные группы BFF endpoint

Ниже — обзор групп. Полная спецификация находится в `CONTRACT.md`.

| Группа | Примеры маршрутов | Назначение |
|---|---|---|
| Служебные | `GET /api/health`, `GET /api/meta` | Проверка BFF/upstream и описание источников |
| Каталог | `GET /api/disciplines`, `GET /api/disciplines/{slug}/subcategories`, `GET /api/categories` | Дерево дисциплин и категорий |
| Поиск | `POST /api/search`, `GET /api/search/suggest` | Выдача, фильтры, фасеты, подсказки |
| Публикации | `GET /api/publications/{id}`, `POST /api/publications`, `.../references`, `.../related`, `.../like`, `.../files/{kind}` | Карточки, библиография, похожие работы, взаимодействия и файлы |
| Авторы | `GET /api/authors/{id}`, `.../stats`, `.../publications`, `.../coauthor-graph` | Профиль, статистика, список работ и соавторы |
| Аналитика | `GET /api/analytics/summary`, `GET /api/analytics/top`, `GET /api/dashboard/{widget}`, `GET /api/graphs` | KPI, рейтинги, виджеты и графы |
| Q&A | `GET/POST /api/questions`, `POST /api/questions/{id}/answers`, `POST /api/answers/{id}/vote` | Вопросы, ответы, голоса |
| Подписки | `POST/DELETE /api/users/{id}/follow` | Подписка/отписка; профиль пользователя |

Для лайков и подписок клиент может передавать `X-Viewer`, для голосования — `X-Voter`. В текущем прототипе это идентификаторы взаимодействия, а не полноценная аутентификация и авторизация.

## 11. Запуск

### 11.1 Требования

Для контейнерного запуска:

- Docker Engine/Desktop;
- Docker Compose plugin.

Для локальной разработки без Docker:

- Go 1.22+;
- Node.js 20+ (Dockerfile использует Node 22);
- Python 3.12+ и `uv` — если запускается встроенный API отдельно.

### 11.2 Только BFF + Web (demo mode)

```bash
docker compose up --build
```

Адреса:

- Web UI: `http://localhost:8088`
- BFF health: `http://localhost:8080/api/health`
- BFF metadata: `http://localhost:8080/api/meta`

### 11.3 Полный стек (full mode)

```bash
docker compose --profile full up --build
```

Адреса:

- Web UI: `http://localhost:8088`
- BFF: `http://localhost:8080`
- Literature API: `http://localhost:8000`
- Swagger UI: `http://localhost:8000/docs`
- OpenAPI JSON: `http://localhost:8000/openapi.json`

### 11.4 API на хостовой машине

Если API запущен вне Docker, можно задать адрес upstream:

```bash
UPSTREAM_URL=http://host.docker.internal:8000 docker compose up --build
```

В PowerShell:

```powershell
$env:UPSTREAM_URL = 'http://host.docker.internal:8000'
docker compose up --build
```

### 11.5 Локальная разработка

BFF:

```bash
cd bff
UPSTREAM_URL=http://127.0.0.1:8000 go run ./cmd/server
```

Frontend (отдельный терминал):

```bash
cd web
npm ci
npm run dev
```

FastAPI (из каталога API):

```bash
cd vendor/literature-api
uv sync --frozen --extra dev
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

### 11.6 Переменные окружения

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `PORT` | `8080` | Порт BFF |
| `UPSTREAM_URL` | `http://127.0.0.1:8000` в бинарнике; `http://api:8000` в Compose | Адрес Literature API |
| `SYNTHETIC_NLP_READY` | `false` | Демонстрационный флаг готовности NLP-зависимых виджетов |

## 13. Какие командные наработки включены в общий проект

По содержимому поставки можно уверенно выделить следующие интегрированные результаты. Здесь перечислены именно артефакты, присутствующие в репозитории; это не попытка приписать конкретные файлы отдельным людям.

### 13.1 Наработки API-команды

В `vendor/literature-api` включён самостоятельный FastAPI-проект:

- 20 публичных операций `/api/v1` и OpenAPI-спецификация;
- типизированные Pydantic-модели запросов, доменные модели и единый формат ошибок;
- разделение router / application / ports / infrastructure;
- mock adapters и общий store в рамках экземпляра приложения;
- fixture-корпус с авторами, категориями, публикациями и библиографическими ссылками;
- образцы PDF и Markdown;
- тесты API и файл проверки/верификации.

Эта работа использована как upstream-контракт и интеграционный источник для BFF. BFF-клиент обращается к API, а документация BFF сохраняет соответствие его сущностям и операциям там, где они доступны.

### 13.2 Наработки UI-команды

В `web` включено самостоятельное React-приложение:

- экраны главной, поиска, публикации, автора, аналитики, Q&A и добавления публикации;
- компонентная библиотека и набор иконок;
- типизированный API-клиент и общие TypeScript-типы;
- диаграммы ECharts и сетевые графы d3-force;
- маршрутизация React Router;
- адаптивная сборка Vite и production-раздача через Nginx.

UI подключён к единому BFF-префиксу `/api`, поэтому страницы не обязаны знать, какой именно источник обслуживает конкретную сущность.

### 13.3 Интеграционная работа платформенного слоя

Общий проект добавляет связующий слой и согласование:

- Go BFF и HTTP-контракт для всех экранов;
- клиент к upstream API;
- объединение API и демо-данных с явной маркировкой источников;
- генератор детерминированного расширенного корпуса и классификатора;
- mock search engine с заменяемым интерфейсом;
- аналитические виджеты и графовые данные;
- Q&A, лайки, просмотры и подписки на стороне BFF;
- Docker Compose, профили запуска, healthcheck и контейнерные образы;
- `CONTRACT.md`, связывающий ожидания фронтенда и BFF.

### 13.4 Что не следует считать уже готовым результатом

Следующие пункты обозначены как точки дальнейшего развития, а не как завершённые производственные возможности:

- постоянная БД и миграции;
- полноценная аутентификация, роли и авторизация;
- реальный поисковый движок вместо `MockEngine`;
- реальные semantic embeddings / hybrid ranking;
- действующий NLP-пайплайн и извлечение понятий/лемм;
- реальная кластеризация и фоновые вычислительные workers;
- внешние DOI/metadata интеграции для автозаполнения;
- долговременное файловое хранилище;
- production observability, rate limiting, секреты и deployment pipeline;
- полноценная синхронизация BFF-состояния между несколькими экземплярами.

## 14. Рекомендованный план дальнейшей командной работы

1. Зафиксировать единую схему идентификаторов, категорий и `source` между API, BFF и frontend.
2. Согласовать, какие сущности должны быть authoritative в API, а какие временно остаются demo/BFF.
3. Подключить постоянную БД к API и/или BFF state, определить миграции и транзакции.
4. Подключить production search engine через `search.Engine`; отдельно определить lexical, semantic и hybrid semantics.
5. Реализовать NLP и фоновые jobs, после чего включать NLP-виджеты только по фактическому readiness.
6. Подключить внешний metadata provider для DOI/названий.
7. Добавить authn/authz и привязать `X-Viewer`/`X-Voter` к реальным пользователям.
8. Уточнить стратегию файлового хранения и ограничения загрузок.
9. Добавить интеграционные тесты полного стека и CI для Go, Python, TypeScript и Docker images.
10. Вести `CONTRACT.md` и OpenAPI как версионируемые источники истины.

## 15. Термины

| Термин | Значение в проекте |
|---|---|
| API / upstream | Внешний по отношению к BFF сервис Literature API на FastAPI |
| BFF | Backend for Frontend — адаптирующий backend для конкретного UI |
| Demo corpus | Синтетические публикации/авторы/категории, генерируемые BFF |
| Fixture | Фиксированный пример данных для теста или mock-адаптера |
| Mock adapter | Заглушка, реализующая контракт без настоящей инфраструктуры |
| Port | Интерфейс, через который прикладной слой зависит от внешней возможности |
| Adapter | Реализация порта конкретной технологией/источником |
| Facet | Агрегированная группа значений фильтра поиска |
| Widget | Самостоятельный блок аналитической панели |
| Graph | Модель узлов и рёбер предметных связей |
| Degraded mode | Работа BFF без upstream, с fallback на демо-источник |
| `source` | Явная метка происхождения данных в ответе |
